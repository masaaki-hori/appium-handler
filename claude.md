# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`appium_handler` is a Dart/Flutter **package** (not an app) that gets embedded into a Flutter app under test. It is the app-side counterpart of a customized Appium Flutter Driver + Appium Inspector stack that makes Appium Inspector work against Flutter apps via `"automationName": "flutter"`. This repo is one of three cooperating repos in that project:

- `appium-flutter-driver` (customized) — forwards `getWindowRect`/`getPageSource`/`performActions`/`findElement` to the app-under-test via the `flutter:requestData` VM-service call (see `driver/lib/commands/screen.ts` and the `executeCommand` overrides in `driver/lib/driver.ts` for the counterpart on that side).
- `appium-inspector` (customized) — GUI that renders the page source, hit-tests taps against it client-side (`utils/element-hit-testing.js`, parsing the same `bounds="[x1,y1][x2,y2]"` format `appium_handler.dart` emits), and records/generates test scripts. For a `flutter` session it always performs a coordinate-based tap (`actions/SessionInspector.js#tapFlutterWidgetAtCoordinates`) and reads back the `{foundBy, value}` the device resolved from the `performActions` response, then two Dart-specific code generators (`lib/client-frameworks/dart-integration-test.js`, `dart-patrol.js`, sharing `dart-common.js#getFlutterFinderExpression`) turn that into a `find.byXxx(...)` expression. This depends on exact string agreement with this package — see below.
- `appium-handler` (this repo) — runs inside the test target app, receives commands, and answers them using Flutter's internal widget inspector APIs.

**Protocol contract with the other two repos (verified compatible as of the last cross-check):** the `foundBy` values this package's `_driveFinder`/`_foundByFor` return (`byTooltip`, `bySemanticsLabel`, `byValueKey`, `byText`, `byType`) must exactly match the strings `dart-common.js#getFlutterFinderExpression`'s switch matches on in `appium-inspector`, since they round-trip through the `performActions` response (`{isError, response: {message: '<our _actionResult JSON>'}}`, per `flutter_driver`'s own `RequestDataResult`/`_requestData` wiring — nothing to change there, it's framework-internal) and are never re-validated at either end. `getFinderType`/`findByPosition` are implemented here but currently have **no caller** in either sibling repo — don't assume they're exercised by anything today. When touching finder-name strings in `_execCommandWithFinder`/`_driveFinder`/`_handleGetFinderType`, grep for the same literal in `appium-inspector`'s `dart-common.js` before renaming anything (a `'byToolTip'` vs `'byTooltip'` capitalization mismatch between `_handleGetFinderType` and `_execCommandWithFinder` was found and fixed here for exactly this reason).

`appium-inspector`'s right-click context menu (Flutter sessions only, added in its `contextメニューに機能追加` commit) drives three more `performActions` action types beyond a plain tap: `checkExistence`, `enterText`, `checkText` (see `SCREENSHOT_INTERACTION_MODE` and `actions/SessionInspector.js#verifyElementExistsAtCoordinates`/`enterTextAtCoordinates`/`checkTextAtCoordinates`), matched 1:1 by the `case 'checkExistence'`/`'enterText'`/`'checkText'` branches in `_performActions` here. That commit's own comments called out that this package's handling of those three cases used to do `_getNodeFromOffset(...)!` — a non-null assertion that **throws if the tapped point has no widget**, crashing the check (not the app-under-test, but the in-progress interaction). The Inspector side works around it with its own client-side pre-check (`findElementAtPoint` against the last-fetched `sourceJSON`) before ever sending these commands, but that's a stale-cache-dependent mitigation, not a fix — this package now guards `node != null` the same way the pre-existing `pointerUp`/tap case already did, so a genuinely missing widget degrades to `'{}'` (surfaced by the Inspector as "couldn't resolve element locator") instead of crashing.

That same right-click menu can present **more than one candidate widget** at the clicked point (overlapping widgets — a `Stack`, a custom-painted touch target layered over other content — are common in real apps), via a submenu built from `findAllElementsAtPoint` (`utils/element-hit-testing.js`, returning every matching node most-specific-first instead of just the first). Picking a specific candidate there threads that widget's page-source `id` through as an `elementId` field on the recorded action (`actions/SessionInspector.js`'s `verifyElementExistsAtCoordinates`/`enterTextAtCoordinates`/`checkTextAtCoordinates`, all now taking an optional 4th `elementId` param); `_performActions`' `enterText`/`checkText`/`checkExistence` cases resolve the target node via a new `_resolveNode(x, y, elementId)` helper instead of calling `_getNodeFromOffset` directly — when `elementId` is present it's looked up by exact `id` match against `_document.descendants`, falling back to the existing coordinate hit-test only when no `elementId` was sent (the single/no-candidate case, and the plain tap flow, which has no disambiguation UI and never sends this field). Resolving by id this way is exactly the same lookup `ById`'s `FinderExtension` already relies on downstream, so no other part of the drive/report chain needed to change.

The consuming app wires this package in with:

```dart
import 'package:flutter_driver/driver_extension.dart';
import 'package:appium_handler/appium_handler.dart';

void main() {
  final handler = AppiumHandler();
  enableFlutterDriverExtension(handler: handler.appiumHandler);
  handler.buildDriverExtension();
  runApp(const MyApp());
}
```

Managed with FVM; pinned Flutter version is in [.fvmrc](.fvmrc) (currently 3.44.6 stable). Prefer `fvm flutter ...` over a bare `flutter` if `fvm` is installed, so the pinned SDK is used.

## Commands

- Install deps: `fvm flutter pub get`
- Static analysis: `fvm flutter analyze` (uses `flutter_lints` via [analysis_options.yaml](analysis_options.yaml)) — should report no issues
- Run tests: `fvm flutter test` — currently a small smoke test in [test/appium_handler_test.dart](test/appium_handler_test.dart) exercising the unknown-command fallback and `getScreenSize`

`pubspec.yaml` intentionally only lists what `lib/` and `test/` actually import (`flutter`, `flutter_driver`, `flutter_test` as SDK deps, plus `xml`; `flutter_lints`/`test` as dev deps). Resist the urge to add packages "just in case" — a much larger, mostly-unused dependency list was previously the main reason `pub get` failed to resolve against newer Flutter SDKs.

## Architecture

Three files in `lib/` divide the work:

- **`appium_handler.dart`** — `AppiumHandler`. This is the entry point invoked by the driver extension (passed as `handler:` to `enableFlutterDriverExtension`, which registers it as the `flutter:requestData` callback). Its `appiumHandler(String? cmd)` method is a switch over command names sent from the Appium Flutter Driver side:
  - `getScreenSize` — returns logical screen size from `PlatformDispatcher`.
  - `getPageSource` — walks the widget tree twice: `layoutTree()` first collects bounds (position/size) per widget via `AppiumWidgetInspectorService.getLayoutExplorerNode`, then `visitorTree()` builds an XML document (`_document`/`_source`) describing every widget with id, key, text, tooltip, semanticLabel, bounds, and center coordinates. This XML is what Appium Inspector's "App Source" view renders and what later commands query against.
  - `getFinderType` / `findElement` / `findByPosition` — look up nodes in the cached `_document` by id, xpath, or screen coordinates, and decide *how* an element should be addressed. (As of the current `appium-flutter-driver` WIP, only `getPageSource`/`getWindowRect`/`performActions`/`findElement` have a driver-side caller; `getFinderType`/`findByPosition` are kept for completeness/future use.)
  - `performActions` — decodes a W3C Actions-style JSON payload (`pointerMove`/`pointerDown`/`pointerUp`/`enterText`/`checkText`/`checkExistence`) and dispatches the resulting tap/scroll/enter_text/check command through `_execCommandWithFinder`.

  `_execCommandWithFinder` separates **how the action is actually performed** from **what locator gets reported** (for Appium Inspector's recorded/generated code), because the most reliable way to do the former (`ById`) can't be used for the latter:
  1. First choice: `ById` (a custom `FinderExtension` in `appium_handler_extension.dart`) resolves the exact widget via `WidgetInspectorService.toObject(id)` on the same page-source `id` every XML node already carries - unambiguous by construction, unlike tooltip/semanticsLabel/key/text/type, which can all be missing or match more than one widget. This requires the `AppiumWidgetInspectorService` instance that minted that id to still be alive, which is why `_getPageSource` now stores it in the `_inspectorService` *instance field* instead of a local variable - `toObject`'s id registry (`_idToReferenceData`) is per-instance, not static. There's no `find.byId` in real `flutter_test` though, so this id can never be the locator a generated test uses.
  2. Whether or not `ById` was used to act, `_computeRecordableLocator` separately determines what locator *should be reported* for codegen, via the tooltip → semantics label → value key → text → widget type priority (first match wins). This is what gets attached as `foundBy`/`value` regardless of how the tap/scroll/enter_text was actually driven.
  3. If `ById` fails (e.g. a stale id from a since-replaced `_inspectorService`), `_execCommandWithFinderChain` is the fallback: it drives the action using that *same* tooltip → semantics label → value key → text → widget type priority, via the shared `_driveFinder`/`_driveKey` helpers (which call into `AppiumHandlerDriverExtension`). Plain `ByType` here is a known-weak step — a runtime type is rarely unique in a real app (any `Icon`/`Text`/`Container` commonly has many instances), so `flutter_test`'s widget lookup throws a "Found N widgets" ambiguity error for it constantly. When that happens (`tap`/`scroll` only), two further fallbacks kick in in order:
     - `ByTypeIndex` (also a custom `FinderExtension`) narrows the same type match to this widget's 0-based position among same-typed nodes in the last-fetched page source (`_typeIndexOf`), via `find.byElementPredicate(...).at(index)`. Reported as `foundBy: 'byType', value: '<Type>#<index>'`; `appium-inspector`'s `dart-common.js#getFlutterFinderExpression` parses the `#index` suffix into `find.byType(X).at(N)`. Only reliable if the element tree's evaluation order is stable between recording and replay.
     - `_driveByCoordinate` synthesizes the gesture directly at the tapped screen coordinate via `AppiumHandlerDriverExtension.prober` (`WidgetController.tapAt`/`dragFrom`), bypassing finder resolution entirely. Deliberately returns no `foundBy`/`value`, since neither `ByType` nor `ByTypeIndex` proved reliable for this widget.

  `enter_text` needed `ById` for a second reason beyond ambiguity: right-clicking a `TextFormField` with no key/tooltip/semanticLabel/text (so it fell through to the ambiguous `ByType` step) silently entered nothing, because `EnterText`/`SetTextEntryEmulation` (see below) ignore whichever finder resolved the field entirely - `ById`'s exact-widget resolution is what made focusing that specific field reliable.

  All finder-based commands (`tap`/`scroll`/`enter_text`/`set_text_entry_emulation`) go through `_callDriverExtension`, not `_driverExtension.call` directly, to work around **two** independent ways `CommandHandlerFactory.waitForElement` can hang indefinitely instead of ever completing on a screen with a repeating animation (a loading spinner, a shimmer effect):
  1. It waits for `SchedulerBinding.transientCallbackCount` to reach zero before/after acting, *only if frame sync is enabled* — never happens while something keeps ticking. Worked around by checking `transientCallbackCount` up front and, if nonzero, disabling frame sync (`set_frame_sync`, already implemented by `CommandHandlerFactory`) for just that one call, restoring it immediately after.
  2. Regardless of frame sync, it *unconditionally* also waits for the finder itself (`finder.evaluate().isNotEmpty`) - and this alone can hang forever if the target widget is never considered hit-testable while polled (seen in practice with a `ByTypeIndex` finder narrowing to one of several `Stack`s under a spinner). `set_frame_sync` has no effect on this wait. Worked around with `_callDriverExtension`'s own `_driverCallTimeout` (2s) wrapping the call: Dart can't cancel the original future, so it keeps polling harmlessly in the background, but `_callDriverExtension` stops waiting on it and reports `isError: true` so the caller's fallback chain (`ByType` → `ByTypeIndex` → `_driveByCoordinate`) moves on instead of hanging.

  Confirmed via timing instrumentation (see git history ~2026-07-15) that `_getPageSource()` itself was *not* the bottleneck (20-134ms even at 800+ nodes) before landing on the above - a multi-minute gap between a `performActions` log line and the next command was the actual signal, and later, a second gap appearing right after a logged `set_frame_sync(false)` (fix #1 alone didn't cover fix #2's case) confirmed there were two distinct hangs to fix, not one.

  `enter_text` has its own gotchas, unrelated to the above: `flutter_driver`'s `EnterText`/`SetTextEntryEmulation` commands (`handler_factory.dart#_enterText`) **ignore whatever finder is sent with them** - `EnterText.deserialize` only reads `text`; it types into whichever widget currently holds keyboard focus (`TestTextInput.enterText`), which is nothing without an actual prior tap. `_driveFinder`/`_driveKey` both call `_focusForTextEntry` for `command == 'enter_text'`, which registers text entry emulation and taps the resolved finder to focus it - regardless of which finder resolved the field, not just `ByValueKey` (the original code only did the emulation-registration half, and only for that one finder type, so `enter_text` silently went nowhere for any field resolved by tooltip/semantics label/text/type or, later, `ById`).

  **Order inside `_focusForTextEntry` matters and is easy to get backwards**: text entry emulation must be registered *before* the tap, not after. `TestTextInput.register()` swaps the platform's `flutter/textinput` channel handler for a fake one that only learns the active connection's client id (`TestTextInput._client`) by intercepting the `TextInput.setClient` platform call the framework makes when a field is focused (`TextInput.attach`). Tap-then-register (this project's first attempt) lets that `setClient` call go to the real platform channel instead, so `_client` is never captured and `EnterText` has no connection to send text to - text is silently dropped with no error. Register-then-tap is correct.

  After a successful `enter_text`, all three drive paths (`_driveById`/`_driveFinder`/`_driveKey`) call `_submitTextEntry`, which sends `send_text_input_action` (`action: 'done'`) - `TestTextInput.receiveAction(TextInputAction.done)` under the hood. `EnterText` only ever updates the field's text; without this, a field's `onSubmitted`/`onFieldSubmitted` never fires, which real keyboard interaction (pressing the on-screen "Done"/return key) would trigger. When this happens, the affected drive path also sets `result['submitted'] = true`, which `_actionResult` includes in its JSON (`"submitted":true`) so the *recorded* action reflects it too - see below.

  **The `submitted` flag has to be threaded all the way to codegen for the generated script to match live behavior**: `appium-inspector`'s `parseFlutterFinderFromResponse` (`actions/SessionInspector.js`) reads it off the `performActions` response into the `flutterFinder` object that gets attached to the recorded action; `dart-integration-test.js`/`dart-patrol.js`'s `codeFor_enterText` then emit an extra `tester.testTextInput.receiveAction(TextInputAction.done)` (patrol: via `$.tester`, since there's no patrol-native shorthand for it) line when `flutterFinder.submitted` is true. Both frameworks' `wrapWithBoilerplate` also needed a new `import 'package:flutter/services.dart';` for `TextInputAction` itself, since `flutter_test.dart` doesn't export it.

  **The actual bug behind a whole round of "Enter Text still does nothing" reports turned out to be entirely on the `appium-inspector` side, not here**: `Screenshot.jsx`'s `x`/`y` React state (the live hover position) gets reset to `null` by `handleScreenshotLeave` the instant the mouse leaves the screenshot div - which happens as soon as the context menu's dropdown overlay appears (the browser re-targets the pointer to the new topmost element), not merely "before the modal's OK button is clicked" as first assumed. `handleEnterTextOk`/`handleCheckTextOk` were reading that same, by-then-`null`, `x`/`y` state, so `performActions` arrived here with a literal `{"x":null,"y":null}` `pointerMove` - traced by adding logging at every step of `_execCommandWithFinder`'s `enter_text` path here and finding all of it unreached, down to the `x!.toDouble()` in `_performActions`'s `enterText` case throwing before its own diagnostic print (placed after the throwing line) could run. A first fix attempt (snapshotting coordinates when the "Enter Text"/"Check Text" *menu item* was clicked) still crashed, because `x`/`y` were *already* `null` by then too - confirmed by logging the values at the menu item's own `onClick`. The actual fix reads coordinates from the right-click (`contextmenu`) event itself, via a `rightClickCoordsRef` populated by a new `onContextMenu` handler on the screenshot div, since that's the only point in the sequence guaranteed to fire before the dropdown steals the pointer. Worth remembering next time text entry "does nothing": check the actual `performActions` payload for null coordinates before suspecting this package's finder/focus logic again.

  Diagnosing this exact failure mode (before the `ByTypeIndex` fallback existed) was a long debugging session (see git history around 2026-07-14) that kept getting derailed by narrow `adb logcat` grep patterns (`'performActions:'`, then `'performActions'`) silently filtering out the very diagnostic prints meant to explain it — when adding ad hoc logging here for a live-device issue, tell whoever is grepping logcat to use the `appium_handler` tag prefix, not a substring of one specific message.

- **`widget_tree.dart`** — `AppiumWidgetInspectorService` (mixes in Flutter's own `WidgetInspectorService`). Exposes widget-tree/layout data that Flutter's public API doesn't surface directly: `getRootWidgetSummaryTreeWithPreviews` (full tree with text previews) and `getLayoutExplorerNode` (per-node render size + global position, pulled from `RenderBox`/`RenderView` internals). Its property-listing method is named `myGetProperties` (not `getProperties`) **on purpose** — `WidgetInspectorService` already defines a public `getProperties(String, String) -> String` (JSON-encoded) with an incompatible signature, so reusing that name is an invalid override. The whole file relies on `@visibleForTesting` framework internals (`InspectorSerializationDelegate`, `objectToDiagnosticsNode`), silenced file-wide via `ignore_for_file: invalid_use_of_visible_for_testing_member` since that's the entire point of this class.

- **`appium_handler_extension.dart`** — `AppiumHandlerDriverExtension`, a copy of `flutter_driver`'s internal `_FlutterDriverExtension`, kept local (and public) so `appium_handler.dart` can hold a reference to it and call `.call(params)` directly once it has resolved a finder for a screen position — `enableFlutterDriverExtension()` doesn't expose its extension instance otherwise. When bumping the Flutter SDK version, diff this file against the current `_FlutterDriverExtension` in `packages/flutter_driver/lib/src/extension/extension.dart` inside the SDK — its method signatures (e.g. `deserializeFinder`/`deserializeCommand` gaining an optional `{String? path}` parameter between Flutter 3.24 and 3.44) are the most likely source of breakage on an SDK bump.

When modifying finder/command behavior, keep in mind the data flows one direction per call: driver command string → `appiumHandler` switch → (for page source) walk widget tree via `AppiumWidgetInspectorService` → cache as XML in `_document` → later commands resolve elements against that cached XML, not a live widget tree query.
