# Design notes

Background and history behind the rules in [CLAUDE.md](../CLAUDE.md): why things are done the way they are, what was tried first, and how the problems were found. `CLAUDE.md` states the rules; this file explains them. Read the relevant section before changing one of these areas.

## Protocol with appium-inspector

- **Finder-name strings round-trip unvalidated.** The `foundBy` values returned by `_driveFinder`/`_foundByFor`/`_computeRecordableLocator` travel back through the `performActions` response (`{isError, response: {message: '<_actionResult JSON>'}}`, per `flutter_driver`'s own `RequestDataResult`/`_requestData` wiring) and are matched by `appium-inspector`'s `dart-common.js#getFlutterFinderExpression` switch without any re-validation at either end. A `'byToolTip'` vs `'byTooltip'` capitalization mismatch between `_handleGetFinderType` and `_execCommandWithFinder` was found and fixed for exactly this reason.
- **Right-click actions used to crash on empty points.** `appium-inspector`'s right-click context menu (Flutter sessions only) drives `checkExistence`, `enterText` and `checkText` (later also `tapDirect`) through `_performActions`. Those cases used to call `_getNodeFromOffset(...)!`, a non-null assertion that threw when the clicked point had no widget, crashing the in-progress interaction. The Inspector side added a client-side pre-check (`findElementAtPoint` against the last-fetched `sourceJSON`), but that depends on a possibly stale cache, so this package also guards `node != null`; a missing widget degrades to `'{}'` ("couldn't resolve element locator" in the Inspector).
- **Overlapping widgets and `elementId`.** The same menu can list several candidate widgets at one point (`findAllElementsAtPoint` in `utils/element-hit-testing.js`, most-specific-first). Picking one sends that widget's page-source `id` as `elementId`; `_resolveNode(x, y, elementId)` looks it up by exact `id` and only falls back to the coordinate hit test when no `elementId` was sent. Ids are re-minted on every `getPageSource`, so a found node is cross-checked against the click point; a stale id that now belongs to another widget usually fails that check instead of acting on the wrong widget.

## Page source

- **Screen-hidden subtrees are excluded (`_collectScreenHiddenElements`).** `Navigator` keeps every previously pushed route in the element tree (the Overlay's `_Theater` keeps entries below an opaque route as offstage children). They used to stay in the XML — often at a negative x, where the Cupertino page transition's parallax leaves them at -width/3. `_typeIndexOf` then counted widgets that `ByTypeIndexFinder` (`find.byElementPredicate`, `skipOffstage: true` by default) never sees, so a recorded `Type#N` pointed at a different widget, and `byText` matched text on screens the user couldn't see. The filter uses the same `debugVisitOnstageChildren` the finders use, limited to screen-level hiders (`_Theater`, `Offstage`, unselected `IndexedStack` children, `SliverOffstage`).
- **Sliver items scrolled out of view are kept.** Sliver/Viewport `debugVisitOnstageChildren` also drops list items outside the viewport, but callers need those to scroll to, so they stay in the XML with an empty `typeIndex` (the finder doesn't see them either). Covered by a lazily built `ListView` test.
- **Debug and Profile builds emit very different trees.** The summary-tree filter that hides framework-internal widgets relies on widget-creation tracking, which only works in Debug (JIT) builds. Debug therefore shows only the app's own widgets (one screen measured at ~80 nodes), while Profile/Release shows everything, framework internals included (~1,600 nodes for one route of the same screen). In Profile/Release, identity-less pass-through wrappers (`_isCollapsibleWrapper`) and zero-size identity-less leaves are left out (`collapsedNodes` on `<tree>`); Debug output is left as is. Making the two identical isn't possible without creation tracking, so everything locators depend on is read from the live tree instead (`typeIndex`, `label`/`hint`, tap-target text).
- **`label`/`hint` come from widget configuration, not rendered text.** The label/hint `Text` of a text field is built inside the framework (`InputDecorator`), so it never appears in a Debug build's page source, and `hintText` disappears from the screen once text is entered. `_inputDecorationTexts` reads `InputDecoration.labelText`/`hintText` from the first `TextField` at or below the node instead. An earlier attempt that matched the rendered label `Text` only worked against a Profile build's XML and failed on a Debug device.
- **Diagnostics on `<tree>`.** `offstageFilter`/`hiddenElements`/`skippedNodes`/`unresolvedNodes`/`collapsedNodes` let an on-device XML dump alone show whether filtering ran. More than once a fix "didn't work" only because the device still ran an old install of the app (with `appium:noReset: true`, Appium doesn't reinstall an app that is already present); a `<tree>` without these attributes means exactly that.

## Driving an action vs. reporting a locator

`_execCommandWithFinder` separates how an action is performed from which locator is reported for generated code:

1. **`ById` performs the action.** A custom `FinderExtension` resolves the exact widget via `WidgetInspectorService.toObject(id)` on the page-source `id` — unambiguous by construction. It needs the `AppiumWidgetInspectorService` instance that minted the id (its `_idToReferenceData` registry is per instance), which is why `_getPageSource` keeps it in the `_inspectorService` field. There is no `find.byId` in `flutter_test`, so it can never be a recorded locator.
2. **`_computeRecordableLocator` picks the reported locator**: tooltip → semantics label → value key → field label → text → tap-target label → `Type#N`.
   - *Field label* (`byFieldLabel`, `<Type>|<label>`, `_fieldLabelLocatorFor`): text fields without a key were otherwise recorded as `Type#N` (shifts whenever a field is added on the same screen) or by their typed-in `text` (useless). Only used when the label is unique among the screen's fields. Dart codegen emits `find.widgetWithText(...)`, which matches rendered text, so a field labeled only by `hintText` can't be found that way after text is entered; JS replay resolves it on the device and has no such limit.
   - *Tap-target label* (`_tapTargetTextFor`): a stock `BottomNavigationBar` item's label is framework-built and absent from a Debug page source, so tapping its icon was recorded as `Container#N`, which pointed at an unrelated 1-px divider at replay. The step walks the live tree to the nearest `InkResponse`/`GestureDetector`/`RawGestureDetector` and uses its single, screen-unique text (an `Icon`'s glyph, drawn as a `RichText`, isn't counted). Replaying a `byText` whose text isn't on the resolved node drives flutter_driver's `ByText` directly, because the resolved node is only the nearest page-source ancestor — possibly the whole navigation bar.
   - *`Type#N`*: N is the live, finder-order index (`_computeLiveTypeIndex`, also emitted as `typeIndex`). Counting page-source nodes instead disagreed with the finder for framework-created types (`InkWell`, `Icon`, `Container`) in Debug and between Debug and Profile.
3. **If `ById` fails** (e.g. a stale id), `_execCommandWithFinderChain` drives with the same priority via `_driveFinder`/`_driveKey`. Plain `ByType` usually fails with "Found N widgets", so for `tap`/`scroll` it falls back to `ByTypeIndex` and finally `_driveByCoordinate` (`WidgetController.tapAt`/`dragFrom`, reports no locator).

## Hangs on animated screens

`CommandHandlerFactory.waitForElement` can hang indefinitely on a screen with a repeating animation (spinner, shimmer), in two independent ways, both handled in `_callDriverExtension`:

1. With frame sync on, it waits for `SchedulerBinding.transientCallbackCount` to reach zero, which never happens while something keeps ticking. Frame sync is turned off for just that call when the count is non-zero.
2. Regardless of frame sync, it waits for the finder itself (`finder.evaluate().isNotEmpty`), which can hang if the target is never considered hit-testable (seen with a `ByTypeIndex` finder narrowed to one of several `Stack`s under a spinner). `_driverCallTimeout` (2 s) stops waiting and reports `isError: true` so the fallback chain moves on; Dart can't cancel the original future, so it keeps polling harmlessly in the background.

Timing instrumentation showed `_getPageSource()` itself was not the bottleneck (20–134 ms at 800+ nodes); a multi-minute gap between a `performActions` log line and the next command was the real signal, and a second gap right after a logged `set_frame_sync(false)` showed there were two distinct hangs.

## `enter_text`

- **flutter_driver ignores the finder.** `EnterText`/`SetTextEntryEmulation` (`handler_factory.dart#_enterText`) only read `text` and type into whatever currently has keyboard focus, which is nothing without a prior tap. `_focusForTextEntry` therefore taps the resolved field, for every finder type (the original code only did this for `ByValueKey`, so text silently went nowhere for fields resolved any other way).
- **Register emulation before the tap.** `TestTextInput.register()` installs a fake `flutter/textinput` handler that learns the active client id only by intercepting the `TextInput.setClient` call made when a field gains focus. Tapping first lets that call reach the real platform channel, so no client is captured and the text is dropped without an error.
- **Submit with `done`.** `EnterText` only updates the text; `_submitTextEntry` sends `send_text_input_action` (`done`) so `onSubmitted`/`onFieldSubmitted` fire like a real keyboard's Done key, and sets `submitted: true` in the response. `appium-inspector` threads that flag into codegen (`codeFor_enterText` emits `tester.testTextInput.receiveAction(TextInputAction.done)`, with an added `package:flutter/services.dart` import).
- **No fallback after an id-based failure.** The chain's `ByType` step for `enter_text` taps a plain, non-indexed type to focus, which with several text fields on screen can type into the wrong one while reporting success (seen on a device after the id-based focus tap timed out because a list virtualized the field away). The id-based failure is returned instead, so the caller re-resolves and retries.
- **"Enter Text does nothing" was once an Inspector bug.** The Inspector read the hover `x`/`y` React state, which is reset to `null` the moment the context-menu overlay steals the pointer, so `performActions` arrived with `{"x":null,"y":null}` and threw before any logging here. The fix reads coordinates from the `contextmenu` event (`rightClickCoordsRef`). Check the actual payload for null coordinates before suspecting this package.

## Debugging on a device

- Narrow `adb logcat` grep patterns (a substring of one specific message) once filtered out the very diagnostic prints meant to explain a failure. Grep by the `[appium_handler]` tag prefix.
- `verboseHitTestLogging` turns on the hit-test path log (`[appium_handler][hitTest]`, up to ~20 lines per coordinate tap). It was the instrumentation that showed a coordinate tap on an AppBar button being delivered to a bottom navigation bar tab; the resolution switched from a reversed document-order heuristic to a real `hitTestInView` (`_hitTestNodeFromOffset`) afterwards.
